# sldb.code lee las claves del SQL de Postgres: PK con IDENTITY, constraints de tabla y FK de ALTER TABLE ADD CONSTRAINT (C4 de IR)

## Rationale

_Explain why this task exists or the business driver behind it._

IR08 mide sobre migraciones reales de Django para Postgres generadas con sqlmigrate y necesita las claves: la PK de Django (id bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY, que tree-sitter-sql 0.3.13 no parsea y hoy se omite), las FK que sqlmigrate escribe como ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY ... REFERENCES ... y las PRIMARY KEY o FOREIGN KEY declaradas al final de CREATE TABLE. Origen: desk/inbox/20261116-211648-suggestion-ir08-ir09-bloqueadas-b2-lee-ts-tsx-js-jsx-y-sql-pero-sldb-api-no-expone-los-facts-c1-c5.md.

## Goal

_Describe the concrete result this task must produce._

Sobre una migración de sqlmigrate de Django para Postgres, sldb.code publica la columna id con su tipo y marca de clave primaria, y un hecho por cada clave (primaria, foránea y única) con sus columnas y, en las foráneas, la tabla y columnas referenciadas, incluidas las que vienen de ALTER TABLE ADD CONSTRAINT.

## Scope

_State what is in scope and what is out of scope._

Entra: (1) una column_definition con error cuyo primer hijo es un identificador se emite igual con ese nombre, el tipo leído del texto hasta el primer error y attrs.parse_partial true; si el texto contiene PRIMARY KEY, attrs.primary_key true. (2) un kind nuevo constraint, hijo de su tabla, para PRIMARY KEY, FOREIGN KEY y UNIQUE de tabla y para cada ALTER TABLE ... ADD CONSTRAINT nombre {PRIMARY KEY|FOREIGN KEY|UNIQUE}; qualified_name <tabla>.<nombre de la constraint> (o <tabla>.pk, <tabla>.fk~N si no tiene nombre); attrs.constraint_type, attrs.columns y, en las foráneas, attrs.references {table, columns}; relación references hacia el hecho de la tabla referenciada si está en el mismo archivo. (3) ALTER TABLE con otras acciones sigue fuera. (4) Ampliar el fixture de Django existente y sus tests; documentar en el docstring de lang_sql.py qué queda fuera. CHANGELOG. No entra: estado acumulado de varias migraciones, otros dialectos.

Precisiones (intento 2): una columna con GENERATED ... AS IDENTITY lleva attrs.identity true además de attrs.primary_key si corresponde. La detección textual de PRIMARY KEY en una column_definition con error se hace sin distinguir mayúsculas, sobre el texto de la columna sin comentarios -- ni literales entre comillas simples. UNIQUE o PRIMARY KEY escritos en la propia columna no crean un hecho constraint: se marcan como attrs.unique o attrs.primary_key en la columna. Las constraints sin nombre se nombran por tipo (pk, fk, unique) dentro de su tabla y las repetidas llevan sufijo ~2, ~3 en orden de aparición, con la misma función de ids.py que el resto.

Precisiones (corrección 2, tras dos testers): toda FK, venga de ALTER TABLE o de CREATE TABLE (constraint de tabla o REFERENCES en la columna), lleva attrs.references {table, columns}; columns vacía cuando la FK no lista columnas referenciadas, que es la clave primaria de esa tabla. Los identificadores entre comillas dobles respetan las comillas escapadas "" ("a""b" es el nombre a"b) en nombres de tabla, de constraint y en las listas de columnas. Los nombres y listas se leen del árbol de tree-sitter donde la gramática los da; la lectura textual queda solo para los nodos ERROR. Lo que siga fuera (CHECK, EXCLUDE, ALTER con otras acciones) va documentado como límite en el docstring de lang_sql.py y en el CHANGELOG.
